Anthropic released Claude Code 2.1.332 on 25 November 2026. One line in its long list of fixes reads "Fixed the terminal freezing, and ignoring Ctrl+C, while a local MCP server floods its standard output". The same release fixed freezes while a hook prints output without end, and resumed conversations sometimes missing their last messages after a crash or kill on Bedrock, Google Cloud's Agent Platform, Foundry and other third-party providers. Six days earlier, 2.1.329 fixed a status line script that prints without end freezing the prompt and using gigabytes of memory.

A local MCP server is a child process. The MCP transport specification says that with stdio the client launches the server as a subprocess and reads newline-delimited JSON-RPC messages from its standard output, and that the server must not write anything else there. A server that floods that channel, with logging or anything else, is writing to the stream Claude Code reads its replies from. Updating fixes this case. The general problem stays: when a terminal program stops reading its input, Ctrl+C stops working too, and that matters most when you are watching from a phone and the machine is somewhere else.

This guide sets up a machine so the Stop button in the shell.online web app can reach it, starts Claude Code under shell, and walks through what to do when the phone's ctrl-c button does nothing: what Stop sends, how long it waits, who is allowed to press it, and how to get the conversation back afterwards.

Step 1: Let your account reach this machine

The terminal link and the Stop button travel different ways. The link carries the screen and your keys. Stop is a command queued in your shell.online account, and a small daemon on your machine collects it. Link the machine first:

shell auth --allow-remote-start
shell daemon status

shell auth opens the approval screen in your browser. Plain shell auth asks, once, whether your signed-in browser may start sessions on this machine. --allow-remote-start agrees without being asked. Saying yes runs the daemon in the background for as long as you stay signed in, and the help says the first yes also installs it as a background service, so it comes back after a restart. shell daemon status says whether your browser can start sessions here.

The help text is blunt about the cost: while this is allowed, anyone signed in to your account can launch processes on the machine, as you, without touching the terminal. If that is more than you want, skip this step and use shell kill from the machine itself (Step 5). An earlier post on starting a session on a Mac that sat idle for days covers the daemon from the other direction.

Two numbers from the code decide whether a Stop gets through. The daemon asks for queued work every 2 seconds (agentPollInterval in cmd/shell/agent_loop.go). The accounts server treats a machine as reachable only if it polled in the last 15 seconds, and refuses a Stop for any other machine rather than queueing it.

Step 2: Start Claude Code under shell

From a plain terminal on the machine, in the project you want to work on:

cd ~/src/example-app
shell --name mcp-trial -- claude -n mcp-trial

shell starts Claude Code in the background and prints a card with the session's name, the link, a ten-character password and a QR code that carries both. The -- ends shell's own flags, so -n mcp-trial goes to Claude Code. The Claude Code CLI reference says -n sets a display name for the session and that you can resume a named session with claude --resume <name>, which Step 6 uses.

Start it from a terminal, not through Claude Code's own Bash tool. shell help start explains that when Claude Code runs shell claude, shell detects the current conversation and starts a fork of it. The CLI reference lists the other start options.

Scan the QR code with your phone. The phone guide shows the page that opens: the terminal, and a row of keys under it that includes esc, enter and ctrl-c.

Step 3: Try ctrl-c first, and read what the screen does

The ctrl-c key sends byte 3, the same byte a laptop keyboard sends. The interactive mode reference says Ctrl+C interrupts a running operation, and that if nothing is running the first press clears the prompt input and a second press exits Claude Code.

When nothing changes, this is why. In a terminal with the ISIG flag set, the line discipline turns byte 3 into SIGINT for the foreground process group, as termios(3) describes. Full-screen programs usually turn that off and read keys themselves. Node's documentation for setRawMode puts it plainly: in raw mode, "Ctrl+C will no longer cause a SIGINT". Claude Code handles Ctrl+C as a key, so the key does nothing until Claude Code's own loop reads it. A loop that is busy with a flood of output does not.

Tap ctrl-c once, then stop tapping. A frozen program does not throw your keys away. The bytes wait in the terminal's input queue until it reads again. If Claude Code recovers with five of them waiting and no turn running, the documented behavior is that the first clears the prompt and the second exits Claude Code. Exiting ends the shell session and closes the link. If one tap changed nothing, go to Stop.

Step 4: Press Stop in the web app

Open app.shell.online on the phone (the app guide describes it) and find mcp-trial in your sessions. The session's own page has a Stop button in its row of actions with Open terminal, and the list has one too. It reads Stopping while the request is sent, and the page reloads the row about a second and a half later, since the machine has to collect the command and report back.

Only the session's owner sees the button, and the server checks again, answering "only the session owner can stop its process" to anyone else. A teammate holding the link can type, including ctrl-c, but cannot press Stop.

What happens after the tap on macOS and Linux, from the code in the shell.online repository:

  1. The app posts a command of kind kill naming the session. The server finds the machine that started it and queues the command for that machine.
  2. Within one 2-second poll the daemon picks it up and runs shell kill with the session's short ID on the machine.
  3. That asks the session's host process, over its local control socket, to stop. The host sends SIGTERM to the whole process group, using a negative process ID the way POSIX kill() defines it.
  4. It waits 2 seconds. If Claude Code is still there, it sends SIGKILL.
  5. The link goes offline, and when the daemon reports the stop done the server closes the session in your list.

The SIGKILL is what matters for a frozen program. One that handles SIGTERM itself has to run its own code to act on it, and a stuck loop may never get there. signal(7) says SIGKILL cannot be caught, blocked or ignored, so the kernel ends the process whatever state it is in.

The process group is Claude Code's own. shell starts the program on a terminal through creack/pty, which starts it in a new session, so Claude Code leads its own group. A local MCP server that Claude Code started stays in that group unless it moves itself out, and gets the same two signals.

If the machine is asleep or offline, the app shows the server's answer instead: the machine "is not reachable, so the stop cannot be delivered", with a pointer to shell auth. For a machine you have since unlinked, it says to stop the session there with shell kill. On Windows, shell ends the process at once with Go's Process.Kill, which calls TerminateProcess, so there is no SIGTERM step and no 2-second wait.

Step 5: Do the same from a laptop terminal

At the machine, or if you skipped Step 1, run the daemon's command yourself:

shell list
shell kill -- <ID>

shell list shows the active shares on this machine and their uptime. shell kill takes the full ID or a prefix of at least 6 characters, prints Stopping with the short ID and the command, and goes down the same path as Step 4.

Step 6: Check for leftovers, update, and resume

An MCP server that moved itself into a different process group, or started its own background helper, will not have received the signals. Look for it by name:

ps -A -o pid,pgid,command | grep '[e]xample-mcp'

Replace example-mcp with the command your server runs. ps(1) prints each process with its process group ID, and the brackets keep grep from matching its own line.

Then update and pick the conversation up again, under a new shell session:

claude update
shell --name mcp-trial -- claude --resume mcp-trial

claude update updates to the latest version, per the CLI reference, which also documents -c for the most recent conversation in the current directory if you did not name the session. On Bedrock, Agent Platform, Foundry or another third-party provider, update before resuming, since that is where 2.1.332 fixed resumed conversations missing their last messages after a kill. The new session has a new link and a new password. Once it is running, open /mcp and look at the servers this project loads before you call the one you suspect again.

What this setup does not do

  • Stop does not unfreeze anything or cancel a turn. It ends the process. Whatever Claude Code was in the middle of stops there, and files it was writing stay as they were at that moment.
  • shell does not know which server flooded or why. It sees bytes on a terminal and signals a process group.
  • It cannot reach a process that left the group, such as a helper that started its own session. Step 6 is how you find those.
  • It needs the daemon and a machine that is awake. A Stop for a machine that has not polled in 15 seconds is refused, not held.
  • Only you can press Stop. Anyone else with the link and password can send keys, so start the session with shell --read-only if a teammate should only watch, and use shell password rotate <ID> if the password went somewhere it should not have. The post on revoking a link without killing the process covers the opposite case from this one, where the process should keep running. The security page lists what each kind of link allows.
  • This is not Claude Code's Remote Control. If the screen is hard to read on a phone, the post on reading Claude Code as a conversation covers the chat view.

Where Pilot Protocol fits

The servers in this story are ones Claude Code runs as its own children. pilot-mcp, Pilot Protocol's local MCP server, is one of that kind: its documentation says it speaks MCP over stdio and runs a fixed pilotctl command against the Pilot daemon on the same machine for each tool, so its standard output is the channel the 2.1.332 fix is about. Pilot Cloud is the other shape. It is a hosted node your client reaches over Streamable HTTP at one endpoint, with no server process on your machine at all. Either way, the Stop button above acts on the Claude Code process, not on the server.

Keep a way out of every session

Link your machine once and you can stop any of its sessions from the web app, whether or not you are at the keyboard. The docs cover the daemon, the link and the phone view.
