OpenCode v2.4.2 was released on 26 November 2026. One of its highlights is called "Esc Takes Back Your Last Message". If the composer is empty and you stop a response with Esc before the model has written anything or called a tool, OpenCode removes your message from the session and puts it back in the composer, images included, so you can edit it and send it again. The same release narrows "Always allow" for a web fetch to the one site you approved, where it used to allow every URL.

The take-back comes from pull request 65505, opened by Tarquinen and merged on 25 November. The description gives the reasoning: interrupting right after sending a prompt usually means you want to reword it, and before this change the prompt stayed in the session as an interrupted turn that you had to clear with /undo or type again. The model's thinking does not count as an answer, so the window can stay open through a long thinking phase.

This matters most when you are steering an agent from a phone, where a prompt typed with your thumbs is the one most likely to go out wrong. A phone keyboard has no Esc key, though, and the obvious substitute, Ctrl-C, does something very different in OpenCode. This guide runs OpenCode under shell.online, opens it on a phone, sends a prompt and takes it back with the esc key on the viewer's key bar, then covers the cases where the prompt does not come back.

What OpenCode 2.4.2 changed

The change applies to both the terminal interface and OpenCode's app. In the TUI prompt component at the v2.4.2 tag, an interrupt takes the prompt back only when all of these hold:

  • The composer is empty. If you have started typing a follow-up, you get a plain interrupt.
  • No other prompt is waiting in the queue for that session.
  • Nothing after your message counts as an answer: no assistant text, no tool call, and no shell command, compaction or synthetic prompt, since each of those starts a run of its own.

When those hold, OpenCode stages a revert of that message with files left alone, commits it at once, and appends the prompt to the composer. There is no "reverted" notice and nothing to redo. The pull request says plainly that file changes are not touched, because there is no redo to bring them back. It is not behind a flag or a setting.

The interrupt itself takes two presses. The OpenCode keybinds reference binds session.interrupt to escape. While a turn runs, the prompt area shows esc interrupt next to a spinner. The first press changes it to esc again to interrupt, and a second press within five seconds sends the interrupt. A press with an autocomplete list open closes the list instead.

Step 1: Start OpenCode under shell

Update OpenCode to v2.4.2 or later the way you installed it, then start it from an ordinary terminal on your computer, in the project you want it to work on:

cd ~/src/example-api
shell --name reword-test opencode

shell starts OpenCode in the background and prints a card. The lines that matter here are Name (the label you gave it), Open (the link), Password (a ten-character session password), Access, which should read view and type · end-to-end encrypted, and Closes, which reads when the task exits. Below that the card prints the commands to rejoin and stop the session, and a QR code labelled Scan to open that includes the link and the password.

Run this from a plain terminal, not through OpenCode's own shell tool. shell help start explains that when OpenCode runs shell opencode, shell detects the current conversation and starts a fork of it, which is a different thing from a fresh session. The CLI reference lists the other start options.

Keep the Closes line in mind. A shell session lasts as long as the program it shares. If OpenCode exits, the link closes with it.

Step 2: Open the link on your phone and find the key bar

Scan the QR code with your phone's camera. The page opens and reads the password from the code. If you open the link some other way, type the password when the page asks for it. The encryption page explains that the password is checked in the browser, and the password prompt itself says it is never sent to shell.online.

Under the terminal you get a row of buttons: a paste button, then esc, tab, four arrows, enter and ctrl-c. The viewer's stylesheet shows this bar when the window is 760 pixels wide or narrower, or when the browser reports a coarse primary pointer through the CSS pointer media feature, which is what a touch screen reports.

Each button sends fixed bytes, defined in web/terminal-keyboard.ts:

  • esc sends byte 27, the ESC control character listed in ascii(7) and defined among the control functions of ECMA-48.
  • The arrows send ESC [ A through ESC [ D, the normal-mode cursor keys in the xterm control sequences.
  • enter sends a carriage return, byte 13.
  • ctrl-c sends byte 3, ETX.

The viewer sends the bytes on pointerdown, the Pointer Events event that fires when your finger touches the button, so a tap goes out without waiting for the finger to lift. The buttons are hidden on a read-only or stopped session, and they are disabled while the page is offline, before the password has been accepted, and while someone else holds the input. In that last case the page says who, for example Local owner is typing… while you type into the session at the computer after shell attach.

Step 3: Send a prompt and take it back

Tap the terminal to bring up your phone keyboard, type a prompt into OpenCode's composer, and tap enter on the key bar. A spinner appears in the prompt area with esc interrupt beside it.

Now take it back:

  1. Tap esc once. The status changes to esc again to interrupt.
  2. Tap esc again within five seconds.

If the model had not yet written text or called a tool, your prompt reappears in the composer and the turn is gone from the session. Edit it with your phone keyboard and the left and right arrows on the key bar, then tap enter to send the new version.

Use left and right to move inside the line. The keybinds reference maps up and down in the composer to the previous and next prompt history items, so the up arrow can walk you away from the text you just got back.

The time that matters is how long the model takes to produce its first word or tool call. A prompt that sends a fast model straight to a tool call leaves you very little time, and the round trip from your phone to your computer adds to it.

Step 4: When the prompt does not come back

If the model had already answered with text or a tool call, the two taps give you an ordinary interrupt and the turn stays in the session. The same happens if your composer held a draft or another prompt was queued. Type the command instead:

/undo

The OpenCode TUI documentation says /undo reverts the latest user message and the work that followed it, and returns the reverted prompt to the composer so you can edit it. /redo restores the reverted work, and sending a new prompt instead accepts the revert. The same page lists Ctrl+X then U as the shortcut for undo. The key bar has no ctrl-x button, so on a phone the typed command is the way in.

Note the difference. The 2.4.2 take-back leaves files alone because the model called no tool before you stopped it. /undo after a tool call is the path that also deals with the work that followed.

Do not reach for ctrl-c. The phone guide describes Ctrl-C as interrupting the running command, and in a terminal with the ISIG flag set the line discipline turns byte 3 into SIGINT, as termios(3) and the POSIX general terminal interface describe. OpenCode reads it as a key instead. Its keybinds reference binds ctrl+c both to "Clear input field" and to "Exit the application", and in the v2.4.2 source the exit binding is active whenever the composer is empty. Tap ctrl-c while a turn runs with an empty composer and OpenCode quits, and with it the session and the link. Tap it right after a take-back and it clears the prompt you just got back. Esc is the key for this job.

Step 5: Stop the session when you are done

Quit OpenCode from the phone by sending /exit as a prompt, or stop the session from your computer. The Stop line on the card gives the exact command with the session's short ID. To find it again later:

shell list
shell kill -- <ID>

shell list shows the active shares on this machine and their uptime, and shell kill stops the process and closes its link. If the link and password went somewhere they should not have, shell password rotate <ID> revokes the password and makes a fresh one while OpenCode keeps running, which an earlier post on revoking a shared link walks through.

If OpenCode did exit by accident, start it again with shell --name reword-test opencode and pick up the earlier conversation with /sessions, which the TUI documentation lists among its common commands. The new run gets a new link and a new password.

What this setup does not do

  • shell knows nothing about OpenCode's turns or composer. The key bar sends bytes, and whether a prompt comes back is decided entirely by OpenCode on your computer.
  • Nothing confirms a tap. If the model started writing between your two taps, you get a plain interrupt, and the screen is the only place you find out.
  • The take-back does not undo file changes, and neither does shell. Anything the model wrote to disk before you stopped it needs /undo or your own git.
  • Anyone with the link and password can tap esc too, or type into the composer. If a teammate should only watch, start the session with shell --read-only, which hides the key bar; the post on read-only links for coding agents covers that setup. The security page lists what each kind of link allows.
  • These steps use the viewer at the link shell prints. OpenCode's own app has the same take-back, but it is a separate program and this guide does not cover it.

If the phone grid looks cramped while you do this, an earlier post on watching an agent without shrinking its terminal explains how the session's size is decided.

Where Pilot Protocol fits

shell.online is developed by the team behind Pilot Protocol, and the two answer different questions. shell gives a person a link to one terminal, so you can reach OpenCode from a phone. Pilot is for the case where the other end is an agent rather than a person: each agent gets a permanent virtual address, and connections run through encrypted tunnels that need a signed mutual handshake first, as how Pilot Protocol works lays out. If you want two agents on different machines to pass work to each other, the Pilot getting started guide installs the daemon, starts a node and walks through a first trust handshake.

For the job in this guide, a person stopping a prompt before it runs, the link is the simpler tool. The source for the viewer and the CLI is in the shell.online repository on GitHub.
