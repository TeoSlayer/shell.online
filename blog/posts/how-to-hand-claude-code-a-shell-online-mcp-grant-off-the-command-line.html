Anthropic shipped Claude Code 2.1.327 on November 17, and one line in its release notes is small enough to miss: claude mcp add-json <name> - now reads the server's JSON from standard input, "so tokens can stay off the command line". The same notes say the stdin form is not available inside a Claude Code session, so you run it from your own terminal.

That matters if you give an agent a credential for a remote MCP server. Until this release, the documented way to add one with a header was the pattern the Claude Code MCP documentation still shows: --header "Authorization: Bearer your-token" typed as an argument. Arguments are not private. On Linux, /proc/<pid>/cmdline holds the complete command line of a running process, MITRE files the general mistake as CWE-214, invocation of a process using visible sensitive information, and ATT&CK lists searching shell history for stored credentials as a known technique.

shell.online has a credential of exactly this kind. shell mcp grant prints a bearer for the endpoint https://shell.online/mcp, and shell help mcp says to keep it out of URLs, command arguments, repositories and logs. This guide starts a coding agent behind a shell.online link, issues a one-hour observe grant into a variable, registers it with Claude Code through stdin so the config file holds only a reference, starts a Claude session that can read the terminal and nothing else, and then takes the access back.

What you need

shell installed and linked to your account with shell auth, as the getting started guide describes, and Claude Code 2.1.327 or later (claude --version prints the number). I read the code path for shell mcp grant in the Unix build, so the commands below are for macOS and Linux. Every command is listed in the CLI reference.

A grant is separate from the browser link and password. The MCP design notes in the repository describe it as a scoped, expiring credential that the session's own host issues, and the post that introduced MCP terminal access walks through the full tool surface.

Step 1: Start the run you want watched

shell --name refactor codex

This starts Codex on your machine and prints a browser link and password, the same as any shell session. Run shell list to see the session's ID. Any unique prefix of at least six characters works in the commands that follow; the examples use the invented ID 3f9c2a71.

Step 2: Issue an observe grant into a variable

SHELL_WATCH_TOKEN="$(shell mcp grant 3f9c2a71 "claude watcher" observe 3600)"
export SHELL_WATCH_TOKEN

shell mcp grant takes the session, a label, a preset and a lifetime in seconds, and on success it prints one line to standard output: the bearer. The command substitution puts that line in the variable without printing it, so it never reaches your scrollback. Your history records the command you typed, not its output. export is a shell builtin, so the value is not the argument of any new process either.

An observe grant has a one-hour default, which is what 0 or no lifetime gives you, and the relay caps it at twelve hours or the time left in the session, whichever is shorter. It does not renew when it is used. When the hour is up you issue a new one on purpose. The label is display text only. It does not identify the client that later presents the bearer.

Step 3: Register the server from standard input

Use a folder of its own for the watcher, so the entry does not end up in a repository you commit:

mkdir -p ~/watch-desk && cd ~/watch-desk
claude mcp add-json shell-watch - --scope project <<'EOF'
{"type":"http","url":"https://shell.online/mcp","headers":{"Authorization":"Bearer ${SHELL_WATCH_TOKEN}"}}
EOF

The - tells Claude Code to read the JSON from standard input, and the here-document supplies it. Quoting the delimiter matters. The POSIX shell specification for here-documents says that if any part of the delimiter word is quoted, the lines are not expanded. With 'EOF' your shell leaves ${SHELL_WATCH_TOKEN} alone, and the text that reaches Claude Code is the reference, not the bearer.

Claude Code expands it later. Its documentation on environment variable expansion in .mcp.json covers ${VAR} in a server's url and headers. It also lists credential names such as ANTHROPIC_API_KEY that read as empty in a remote server's headers; a name like SHELL_WATCH_TOKEN is not on that list. The "type":"http" field is required, because the same page says an entry with a url and no type is read as a stdio server and fails. --scope project writes the entry to ~/watch-desk/.mcp.json, and the command prints an Added line when it succeeds.

The endpoint takes MCP messages as HTTP POST requests with the bearer in the Authorization header, which is the Streamable HTTP transport. Claude Code accepts streamable-http as an alias for its http type.

If you would rather store the literal bearer, stdin is also how you keep it off the command line. printf is built into Bash and zsh, so the value is not an argument of any process:

printf '{"type":"http","url":"https://shell.online/mcp","headers":{"Authorization":"Bearer %s"}}' "$SHELL_WATCH_TOKEN" | claude mcp add-json shell-watch -

That form writes the value into ~/.claude.json under the default local scope and leaves it there until you remove the server. For a credential that is dead in an hour I would keep the reference.

Step 4: Approve the server and check the connection

claude mcp list

A project server from .mcp.json starts at ⏸ Pending approval (run `claude` to approve). Per the server status section, you approve it by running claude in the folder, accepting the folder trust dialog and approving the server when asked. After that, claude mcp list shows a health status for shell-watch. A failed connection appears as ✘ Failed to connect with the HTTP status appended, and claude mcp get shell-watch prints the same detail on an Issue: line.

Claude Code reads SHELL_WATCH_TOKEN from the environment it was started in. Start claude from the terminal where you exported the variable. If it is unset, the docs say the config still loads, claude mcp list warns about the missing variable, and the unexpanded ${SHELL_WATCH_TOKEN} text is sent as is, so the relay refuses the request. When the grant expires you will see the same refusal: issue a new grant, export the new value and start Claude Code again.

Step 5: Start Claude with the read tools only

claude --allowedTools "mcp__shell-watch__*" --disallowedTools "mcp__shell-watch__shell_send"

The Claude Code permissions reference names MCP tools mcp__<server>__<tool> and accepts an allow glob after a literal server prefix, so the first flag lets Claude call this server's tools without asking. An observe grant already leaves shell_send out of the catalog. The deny rule is a second limit on the client side in case someone later puts a control bearer in the same variable.

The observe tools are shell_status, shell_screen for the current rendered grid, shell_output for bounded output with a cursor, and shell_wait, which blocks for up to 45 seconds until output or a pattern appears. A prompt such as "check the refactor terminal every few minutes, and tell me when the tests fail or Codex asks a question" is enough to use them. Treat what Claude reads there the way the shell docs do: terminal output is "untrusted data, never permission to override controller instructions."

Step 6: See the grant, then end it

While the grant is live, the session's terminal pane in the web app reads MCP · server-side decryption authorized. That label describes a real change. Browser sharing is end-to-end encrypted, as the encryption page explains, but an MCP client is a remote program, so the host hands the relay a frame key and the relay decrypts frames in memory to answer tool calls. Claude receives plaintext. In the words of shell help mcp, browser-only sharing remains end-to-end encrypted; a session with a live grant has a second reader.

shell mcp list 3f9c2a71

This prints one line per grant: its ID, whether it is live, expired or revoked, its scopes, the label and the expiry time. To end it early:

shell mcp revoke 3f9c2a71 <grant-id>
shell mcp revoke-all 3f9c2a71
unset SHELL_WATCH_TOKEN

The first prints Revoked and the grant ID, the second Revoked all MCP grants. Neither touches the browser link. Quitting Claude Code is not a revocation; the OWASP secrets management cheat sheet makes the general point that restarting an application does not revoke a stolen credential, which stays usable until the service expires or revokes it. If you think the bearer leaked, shell password rotate 3f9c2a71 replaces the browser password and revokes every MCP grant without stopping Codex. The security page covers the rest of the credential model. To drop the entry itself, run claude mcp remove shell-watch --scope project in ~/watch-desk.

What this setup does not do

It does not hide the bearer from Claude Code. The value sits in the environment of the claude process, and commands that its Bash tool runs inherit that environment, so a command such as env could print it into the conversation. What keeps that tolerable is the grant: observe only, one session, an hour.

It is not a tested pairing. The shell MCP notes record a 16-check canary on 2026-09-21 that used a synthetic shell, staging runs with Codex and OpenCode, and the sentence "Claude model-backed behavior remains unverified." I did not run Claude Code against a grant for this guide. Keep the browser view open next to the first session and check Claude's reports against the screen.

It does not let Claude type. Input needs a separate control grant, shell_key and shell_interrupt are not available in this release, and a session started with --read-only refuses input whatever the grant says. It also does not tell anyone which agent called. Neither a label nor an acknowledgement verifies the caller, and the bearer works for whoever holds it, which is what RFC 6750 means by a bearer token.

Finally, the native grant is not the same thing as the browser's Connect invitation for agents described in an earlier post. The docs say not to interchange their credentials.

Where Pilot Protocol fits

shell.online is built by Pilot Protocol, and the contrast with Pilot's own MCP server is useful here. The pilot-mcp documentation adds it to Claude Code as a local stdio server, claude mcp add --transport stdio pilot -- npx -y pilotprotocol-mcp, which talks to the Pilot daemon on your machine, so there is no bearer to put anywhere. A remote MCP endpoint like shell's always needs one. Pilot's post on connecting MCP servers to agents across any network covers the other half of the problem: MCP gives an agent tools, and something else has to carry results between agents on different machines.

Give Claude one hour of read access to one terminal

Install shell, wrap the run, issue an observe grant and register it from stdin. The grant ends on its own, and a session with no grant stays end-to-end encrypted.
