Anthropic published Claude Code 2.1.328 on GitHub early on 19 November 2026. Its first line adds auto mode for Claude Opus 4.6 and Sonnet 4.6 on Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry and the Claude apps gateway, and says that interactive sessions with no permission mode start in it. In auto mode, as the permission modes page puts it, a second model called the classifier reviews actions instead of you.

The same page says auto mode has been the built-in starting mode for interactive sessions since v2.1.283, but on those providers it lists only newer models: Sonnet 5 or later, Opus 4.7 or later, Haiku 5.5 and the Fable models. A team that pinned its models to Opus 4.6 or Sonnet 4.6 on Bedrock, and the Claude Code on Amazon Bedrock guide tells you to pin versions before a rollout, did not get auto mode. After the update it does, without anyone passing a flag. The same applies on Microsoft Foundry, where Sonnet 4.6 is one of the Claude models you can deploy.

That matters if you start Claude Code from your phone with shell.online. The web app's New session sheet builds the command from a short form, and with the "Skip permission checks" toggle off the command is plain claude. That is a session with no permission mode. This guide pins the mode a session starts in on the machine itself, starts one from the phone, and reads the mode back off the screen. It also covers why a provider setting in your shell profile may never reach a session the app started.

What the app sends to your machine

The form lives in app/src/lib/session-kinds.ts in the shell.online repository. For Claude Code it has four fields: a resume session ID, a model, the skip toggle and a session name. The builder turns them into one line. A resume ID adds --resume, a model adds --model with opus, sonnet or haiku, and the toggle adds --dangerously-skip-permissions.

The sheet shows that line under the form before you press Start session, and the daemon on your machine runs it as given.

Claude Code then picks its starting mode from the first of three sources that applies: the --permission-mode flag (or --dangerously-skip-permissions), then permissions.defaultMode in a settings file, then the built-in default. So the toggle wins over every settings file, and with the toggle off a settings file is the only thing that sets the mode before the built-in default does.

Step 1: Check what the machine will run

At the machine, check the version:

claude --version

Anything at 2.1.328 or later has the new behavior. Then look at your user settings:

jq '{env, permissions}' ~/.claude/settings.json

On a machine set up with the Bedrock wizard you will see an env object holding CLAUDE_CODE_USE_BEDROCK, the AWS profile or region, and any model pins such as ANTHROPIC_DEFAULT_SONNET_MODEL. If permissions prints null or has no defaultMode, a session from the app will start in whatever the built-in default is for your model and provider, which after this release is auto mode for the 4.6 models as well.

A provider exported in your shell profile may not reach the phone's session. A session the web app starts is a child of shell's background daemon and gets the daemon's environment, not the environment of the terminal you happen to have open. When the daemon runs as the installed service, the service file shell writes (a launchd plist on macOS, a systemd user unit on Linux) carries at most six variables, all starting with SHELL_ONLINE_, and only the ones that were set when you installed it. You can read the list in cmd/shell/service.go; on Linux they become Environment= lines, which systemd.exec documents. An export CLAUDE_CODE_USE_BEDROCK=1 in ~/.zshrc is read by your interactive shell. launchd and systemd do not read that file, and the variable is not one of the six. Keep the provider in the env block of ~/.claude/settings.json, so a session started from the phone talks to the same provider as one started at the keyboard.

Step 2: Pin the starting mode in your user settings

Settings files are strict JSON. The JSON grammar in RFC 8259 has no comments and no trailing commas, and Claude Code reports a file that breaks it as a Settings Error. Editing by hand is fine, but jq keeps every key you already have and adds the one you want:

mkdir -p ~/.claude
test -f ~/.claude/settings.json || echo '{}' > ~/.claude/settings.json
jq '.permissions.defaultMode = "default"' ~/.claude/settings.json > ~/.claude/settings.json.new \
  && mv ~/.claude/settings.json.new ~/.claude/settings.json
jq '.permissions' ~/.claude/settings.json

The first two lines create an empty file if there is none. The third writes a copy with permissions.defaultMode set and moves it into place, and the last prints the result:

{
  "defaultMode": "default"
}

If you already had allow or deny rules they print alongside it. The value default is the mode Claude Code now labels Manual, and the CLI also accepts manual as an alias. In Manual mode only reads run without asking. If you would rather let it edit files and run common filesystem commands such as mkdir and mv, and still ask before other shell commands, use acceptEdits instead.

Two details are worth knowing. If CLAUDE_CONFIG_DIR is set, Claude Code reads its settings from there rather than from ~/.claude. And if your settings file is a symlink into a dotfiles repository, the mv above replaces the link with a plain file, so edit the target instead.

The user file applies to every project on the machine, which is what you want when you do not know which folder the phone will start a session in. The settings precedence page gives the order. A project's own .claude/settings.json sits above it, so a repository can still set acceptEdits or plan for itself. The same page says the values auto and bypassPermissions do not take effect from project or local files, so a repository cannot quietly switch you into either one.

Step 3: Start the session from your phone

The machine has to be linked and allowed to take browser starts. If you said no when shell auth asked, run shell auth --allow-remote-start at the machine. Then check that the daemon is there:

shell daemon status

It says whether your browser can start sessions on this machine. On the phone, open app.shell.online, press New session, and choose Claude Code. Leave Skip permission checks off. Under Model, "Whatever the machine is set to" adds nothing to the command, while Opus, Sonnet or Haiku add the alias. On Bedrock an alias resolves to the pin in ANTHROPIC_DEFAULT_OPUS_MODEL or ANTHROPIC_DEFAULT_SONNET_MODEL when one is set, and the guide's own pinning example maps Sonnet to us.anthropic.claude-sonnet-4-6, a cross-region inference profile for Sonnet 4.6.

Pick the machine under Run on and read the preview line. It should say $ claude or $ claude --model sonnet, with no --dangerously-skip-permissions. Press Start session.

Step 4: Read the mode off the screen

Claude Code prints its mode in the status line under the prompt. The permission modes page lists the strings: ⏸ manual mode on for default, ⏵⏵ accept edits on, ⏸ plan mode on, ⏵⏵ auto mode on and ⏵⏵ bypass permissions on.

If you watch Claude Code in the app's Chat renderer, you will not see that line. The Claude Code reader in the app treats status lines as noise on purpose, because spinners and timers change every frame and would otherwise arrive as a message per repaint, and the mode line matches the same pattern. Set Renderer to Adaptive or Fixed grid and the status line is there with the rest of the screen. The post on reading Claude Code as a conversation describes what the Chat view keeps and drops.

If the line says ⏵⏵ auto mode on after Step 2, type /status into the session from the phone. Its Status tab has a Setting sources line that lists every settings file Claude Code loaded. If User settings is missing, the file did not load or is broken. If a managed source is listed, your organization's settings sit above your own file and may set the mode for you. On Bedrock, /status also shows the resolved region, which is a quick way to confirm the session reached the provider you expected.

Step 5: Choose auto mode on purpose

Pinning Manual as the default does not take auto mode away. For one run where you want it, start the session from a terminal on the machine and pass the flag, which beats the settings file:

shell --name nightly-refactor -- claude --permission-mode auto

shell prints a link and a ten-character password and returns, and the session shows up in the app under that name. An administrator who sets disableAutoMode to "disable" in managed settings removes auto from the cycle entirely, and a session started with --permission-mode auto then starts in Manual.

To change the mode of a session that is already running, go to the machine, run shell list to find its ID, then shell attach <ID>. Press Shift+Tab to cycle: from auto the first press goes to default, then acceptEdits, then plan. Press Ctrl-X, release it, then press D to detach and leave the process running.

I would not plan on cycling modes from a phone. A phone keyboard has no Shift+Tab, and the Chat renderer's direct key handling sends a plain Tab even when Shift is held.

What this setup does not do

  • shell does not know or enforce Claude Code's permission mode. It runs the command it is given and carries the screen and your keystrokes. The prompts, the classifier and the settings files are all Claude Code's.
  • The web app's form has no permission mode field. Its only permission control is the skip toggle, and that one overrides any settings file you write.
  • defaultMode decides how a session starts. A session that is already running keeps the mode it is in until someone changes it there, so read the status line rather than assuming.
  • The setting is per machine and per user account on that machine. A second computer linked to the same shell.online account needs its own file.
  • Managed settings from your organization beat your user file. If they set the mode, the value from Step 2 is ignored.
  • Manual mode is not a safety net for an unattended run. A prompt nobody answers simply waits, and the run sits there until you get to it. The earlier guide to watching an agent after you turn off its prompts covers the opposite trade.

OWASP's entry on excessive agency recommends human-in-the-loop approval for high-impact actions. Auto mode moves that approval to a classifier, so before it runs on a machine with production credentials you should decide that is acceptable rather than inherit it from an update. The security page describes what shell itself exposes to a viewer, and the post on browser starts on an idle Mac covers the launchd side of the daemon.

Where Pilot Protocol fits

shell.online is built by the team behind Pilot Protocol, a networking stack for autonomous agents, and the question here, who decides what an agent may do without asking, comes up there between agents. Pilot's open source rendezvous has owner, admin and member roles, and only owners and admins can set network policy, as the post on RBAC, policies and the audit trail describes. That is the same split as managed settings sitting above a developer's own Claude Code file. And agents on a Pilot network only exchange data with peers they have verified, which the post on mutual trust between agents goes through.
