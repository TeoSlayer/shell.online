Anthropic shipped Claude Code 2.1.323 on 12 November with a small addition for anyone who starts Claude Code from another program: CLAUDE_CODE_RESUME_HINT_COMMAND. The release note says a program that starts Claude Code can set it "to have the exit hint name its own resume command". The environment variable reference fills in the rest. You set it to the name you type to run your wrapper, and a local session then prints mytool --resume <session-id> at exit instead of claude --resume <session-id>. A day later, 2.1.325 fixed recent turns sometimes going missing from a resumed session after Claude Code stopped without a clean exit.

This matters if you run Claude Code through shell.online. When a shared session's process exits, the link stops being live. If you then resume with a plain claude --resume, the conversation comes back in a local terminal with no link at all, and the teammate who was watching has nothing to reload. The exit hint pointed you at the wrong command.

This guide builds a short wrapper script that fixes both halves. The wrapper sets the new variable, so the hint names the wrapper. The wrapper starts Claude Code through shell --persistent, so every run, including a resume, comes back on the same URL and password. I checked the shell behavior below against the shell.online source for the 0.25.0 release, on its macOS and Linux code path, and the Claude Code side against Anthropic's documentation for 2.1.325.

Step 1: Check both versions

The variable does nothing on older Claude Code builds, so check first:

claude --version
shell --version

The first prints something like 2.1.325 (Claude Code); you need 2.1.323 or later. The second prints shell 0.25.0, the latest published CLI release. If shell is missing, the platforms page has the installers, and the command reference lists every flag used below.

Step 2: Write the wrapper

Put the script in a directory that is on your PATH. This example uses ~/.local/bin:

mkdir -p ~/.local/bin
cat > ~/.local/bin/claude-shared <<'EOF'
#!/bin/sh
# Start Claude Code behind one persistent shell.online link.
export CLAUDE_CODE_RESUME_HINT_COMMAND=claude-shared
exec shell --persistent "${XDG_STATE_HOME:-$HOME/.local/state}/claude-shared/link.json" \
  --name "claude-shared" -- claude "$@"
EOF
chmod 755 ~/.local/bin/claude-shared

Line by line:

  • export CLAUDE_CODE_RESUME_HINT_COMMAND=claude-shared puts the name in the environment. On Unix a child process inherits a copy of its parent's environment, and shell starts the wrapped command with the calling environment minus a few of its own internal variables, so Claude Code sees it. The docs say Claude Code ignores this variable in a settings file's env block, which is why it lives in the script.
  • exec replaces the script with shell, and "$@" hands every argument you typed to claude unchanged. The POSIX shell specification defines "$@" as one field per argument, and zero fields when there are none.
  • --persistent names a state file. The XDG Base Directory specification reserves $XDG_STATE_HOME, by default ~/.local/state, for state that should persist between application restarts, which is what this is. shell creates a missing directory with mode 700 and writes the file with mode 600.
  • --name labels the session in shell list, shell ls and the web app. The -- ends shell's options so nothing after it is read as a shell flag.

The state file is a credential. It holds the session ID, a host token, the browser password and the encryption key. Anyone who copies it can bring the link up from their own machine, so keep it out of any repository and any synced folder.

The variable takes a single name, not a command line. Claude Code ignores any value that does not match ^\w[\w-]*$, and in that pattern \w means letters, digits and the underscore. Setting it to "shell claude" is silently ignored because of the space, and the hint goes back to claude --resume. That is why this guide uses a wrapper with a one-word name.

Step 3: Start a session and share it

Go to the project and run the wrapper as you would run claude, with or without a prompt:

cd ~/src/payments-api
claude-shared "Read the failing tests in tests/billing and propose a fix"

shell prints a link, a password and a QR code, then returns your prompt while Claude Code runs in the background. The first run creates the state file. Send the link and the password to your teammate by different channels, as the encryption guide suggests for anything sensitive.

Decide now whether the link should be view-only. Access mode is fixed when the state file is created. If you add --read-only to the wrapper later, the next start stops with shell: persistent state access/encryption mode does not match the requested flags. A read-only link blocks your own browser input too; you would then type through shell attach on the machine. The security page covers the trade.

On a machine linked with shell auth, shell also adds two flags of its own when it launches a fresh claude: --settings with a SessionStart hook that writes to a private file, and --session-id with a new version 4 UUID. They exist so owner-only summaries describe the right conversation. They matter in the next step.

Step 4: End the conversation and read the hint

When you are done for now, type /exit in the browser, or run shell attach <ID> on the machine and exit there. Claude Code prints its "Resume this session with" line, which now names the wrapper:

claude-shared --resume 0b7e4c2a-5f1d-4e8b-9a36-2c4d8e1f7a90

That ID is an invented example. Since 2.1.317, Claude Code repeats the flags you launched with ahead of --resume, so on a linked machine the printed line can carry the --settings or --session-id value shell added. Copy only claude-shared --resume and the ID. shell adds what it needs again on the next launch.

A persistent session does not end the way an ordinary one does. In the relay's exit handler, a persistent task exit marks the session disconnected rather than ended. A browser that was watching keeps the last screen the machine sent, under a notice headed "Temporarily offline". That screen should include the resume line. If it does not, Step 6 has two other ways to find the conversation.

The same handler clears every MCP grant on the session. If another agent was watching over MCP, issue it a new grant with shell mcp grant <ID> <label> observe after you resume. The agents guide and the post on scoped MCP grants explain the scopes.

Step 5: Resume on the same link

From the same project directory, run the line from the hint:

cd ~/src/payments-api
claude-shared --resume 0b7e4c2a-5f1d-4e8b-9a36-2c4d8e1f7a90

shell reads the state file, reserves the same session ID and reconnects to the relay with the stored host token. It prints the same link and the same password as the first run. Claude Code loads the conversation from its transcript and waits for your next message.

Your teammate does nothing. The notice they were looking at says the terminal "reconnects on its own, and the terminal goes live again when it does", and that is what happens when the host comes back with the same identity and key. Someone who closed the tab opens the same link and enters the same password. The reliability guide lists what a viewer sees while a host is away.

Step 6: Find a conversation without the hint

Because the wrapper passes every argument to claude, Claude Code's own ways of choosing a conversation work through it. The CLI reference describes both:

claude-shared --resume
claude-shared --continue

--resume with no ID shows an interactive picker, which you can answer from the browser on your phone because it runs inside the shared session. --continue loads the most recent conversation in the current directory, so run it from the project you were working in. You can also give a conversation a name when you start it, with claude-shared -n billing-fix, and later resume it with claude-shared --resume billing-fix. Claude Code's -n is not shell's --name; the first names the conversation, the second names the shared session.

What this setup does not do

  • It does not save the process. Resuming reloads the conversation from Claude Code's transcript. Commands that were running, dev servers and background shells are gone. shell's own command reference says --persistent does not restore process memory.
  • It runs one conversation per state file. A second claude-shared while the first is still running stops with session is already running locally or has a retained record; recovery is needed before replacement. For two parallel conversations, make a second wrapper with its own name and state file.
  • It does not recover from a crash by itself. A crash that leaves a local record or control socket blocks resuming that persistent session until you review it, and nothing restarts automatically. The 2.1.325 fix is about Claude Code's transcript after an unclean stop; it does not change shell's check.
  • It keeps a credential alive for a long time. shell's lifetime rules keep a disconnected persistent session for 30 days, against 12 hours for an ordinary one, and each exit restarts the 30 days. The OWASP Session Management Cheat Sheet recommends an absolute timeout for every session; this link has none while you keep using it. Run shell password rotate <ID> when someone should lose access, as the post on revoking a link without killing the process shows.
  • It covers macOS and Linux. The wrapper is a POSIX sh script, and I checked the Unix code path only.

Where Pilot Protocol fits

The state file is the whole trick here: the link survives because the identity lives in a file on your disk, not in the running process. Pilot Protocol, which develops shell.online, uses the same idea for agents on its network. Its post on persistent addresses for distributed agents ties each agent's address to its cryptographic identity rather than its network location, and notes that consistent key material is what keeps that address stable across restarts. The Pilot blog also covered a persistent shell.online link across a reboot, which pairs with this guide when the machine itself restarts. The source for everything above is in the shell.online repository.
