Claude Code version 2.1.329, released on November 19, 2026, made a session's own schedule visible in one place. The release adds "this session's scheduled tasks, /loop wakeups, the goal and this conversation's forks to /tasks", and pressing x on one of them stops it after asking. The scheduled tasks page also describes the older route, asking Claude to list them, and that still works.

The scheduling itself lives inside the process. Anthropic's page on running prompts on a schedule says the tasks are session-scoped and fire only while Claude Code is running and idle. Closing the terminal stops them. A recurring task expires seven days after it was created, and a fixed-interval loop such as /loop 30m ignores Esc and Ctrl+C: you stop it by asking Claude to cancel it. OpenCode moved the same way today, when OpenCode 2.4.0 added automations that run prompts, scripts or shell commands on a timer or a cron schedule. This guide sticks to Claude Code, because its documentation says exactly where its tasks run.

If the loop lives as long as the process, then the process lifetime is the one setting you control from outside Claude. This guide runs Claude Code under shell.online with a closing time, starts a loop, checks the schedule from a phone with /tasks, and explains what happens to the remaining wakeups when the deadline arrives.

Step 1: Start Claude Code with a closing time

shell wraps a command in a terminal, prints a browser link and a password, and leaves the command running in the background. The --auto-close option adds a deadline. Run this from the repository the loop should work in:

shell --name pr-1234-loop --auto-close 07:30 claude

The CLI reference lists the forms --auto-close accepts: a duration such as 8h or 1h30m, an RFC 3339 timestamp, YYYY-MM-DD HH:MM, a bare HH:MM, or today and tomorrow with an optional time. Multi-word forms can be typed without quotes, as in --auto-close tomorrow 07:30. A bare 07:30 means the next 07:30: the parser in cmd/shell/autoclose.go moves a clock time that has already passed today to tomorrow. A missing or invalid value exits with status 2 and is never mistaken for the command.

The start card names the session, prints the link and the password, and adds a line for the deadline, along these lines:

Closes 2026-11-24T07:30:00+01:00, or when the task exits

That is the one-line summary of the whole setup. The session ends at 07:30 or earlier if Claude Code exits on its own. Put options before the command; everything after claude goes to Claude Code.

Step 2: Start the loop and detach

The session is in the background, so attach to it from the same machine. shell list prints the session ID, and a prefix of at least six characters is enough:

shell list
shell attach 3f9c2a

Answer the folder trust dialog if Claude Code shows one, then type the loop:

/loop 30m run gh pr checks 1234 and, if a job failed, read its log and tell me why. Do not push.

Claude converts the interval to a cron expression, schedules the job and confirms the cadence and an 8-character job ID. gh pr checks prints the CI status of one pull request, and the prompt keeps the loop to reading. The cron format is the standard five fields described in the POSIX crontab specification, and all times are local.

Press Ctrl-X, then D, to detach. Detaching leaves the process running, which is what keeps the loop alive. If you leave out the interval and type /loop check whether CI passed, Claude chooses a delay between one minute and one hour after each iteration instead, and the loop shows up in the task list as a pending one-shot wakeup.

Esc and Ctrl+C do not stop a fixed-interval loop. The phone's key bar has esc and ctrl-c buttons, and on a self-paced loop Esc on an empty prompt cancels the pending wakeup. A /loop 30m ignores both. To end it before the deadline, open /tasks and stop it there, or type "cancel the CI check loop" and let Claude call CronDelete.

Step 3: Check the schedule from your phone

Open the link on your phone and enter the password. In a browser window 760 CSS pixels wide or narrower, or on any device whose primary input is a finger (the coarse pointer case in CSS), the page shows a row of keys under the terminal: esc, tab, the four arrows, enter and ctrl-c. The mobile guide covers the rest of the phone view.

Type /tasks and tap enter. On 2.1.329 or later the list includes the loop you scheduled and any pending wakeup. If you would rather read the raw schedule, ask "what scheduled tasks do I have?" and Claude answers with a CronList call whose rows show each task's ID, schedule and next run time.

That next run time will not match the cron line exactly. Claude Code adds jitter so that sessions do not all call the API at once. Per the docs, a task every 30 minutes runs 0 to 15 minutes late, and an hourly or daily task runs up to 30 minutes late. Only /loop 5m, written */5 * * * *, runs early instead, 4 minutes 45 seconds after the previous run. Keep that in mind when you pick the deadline: a 30-minute loop with a 07:30 cutoff can start its last run as late as 07:15.

The phone is also where you answer prompts. A fired iteration goes through the session's permission checks, so if gh needs approval at 03:00, the run waits at that prompt until someone answers it. The arrows and enter on the key bar are enough to choose an option.

Step 4: Read the deadline back from the machine

At the desk, shell list in a wide terminal has a CLOSES column. A session with a deadline shows the time left in at most two units, such as in 9h12m, and one without a deadline shows on exit. In a narrower window the list switches to one block per session, where the same value reads in 9h12m, or when the task exits. For a script, the JSON form carries the absolute time and the seconds left:

shell list --json | jq '.[] | {name, closes_at, closes_in_seconds}'

Pick fields with jq as above rather than printing the whole array, because shell list --json includes each session's browser password in e2ee_password.

Step 5: Know what happens at 07:30

I read the Unix code path for this step, in cmd/shell/session_unix.go and cmd/shell/process_unix.go. When the deadline passes, shell sends SIGTERM to the wrapped process's whole process group, using a negative process ID as kill(2) describes. It waits two seconds. If the process is still alive, it sends SIGKILL, which signal(7) lists as a signal that cannot be caught. The browser link closes with the process. The Windows build skips the SIGTERM step and kills the process outright.

Once Claude Code has exited, no task fires, because the scheduler runs inside it. That is the outer bound this guide is after: the seven-day expiry stops a forgotten loop after a week, and the deadline stops it at the hour you chose.

The deadline does not delete anything from Claude's side, though. The scheduled tasks page says claude --resume and claude --continue restore tasks created with CronCreate unless a recurring task has expired or a one-shot task's time has passed. A self-paced loop is not restored. If you resume the conversation the next morning, check /tasks before you leave it running again.

What this setup does not do

  • It does not keep the computer awake. A sleeping laptop runs no loop. On a Mac, caffeinate holds off idle sleep; on Linux, systemd-inhibit does the same for a command you wrap.
  • It is not a cloud schedule. Anthropic's cloud scheduled tasks run without your machine on. A /loop under shell needs the machine on, the network up and the session open.
  • It does not pause anything. A deadline ends the process. There is no option to suspend a loop overnight and continue it later.
  • It does not undo work. If an iteration pushed a commit or posted a comment before 07:30, that stays. A loop that can act on its own is the case OWASP files under excessive agency, which is why the prompt in Step 2 only reads.
  • It does not limit who can type. Anyone with the link and the password can add a loop or cancel one. To cut off a teammate without stopping the run, use shell password rotate, as in revoking a shared link without killing the process. The security page describes what the relay can and cannot read.
  • It does not tell you when a run fails. You see the result when you open the link. The session pulse shows which session is waiting on you, and that is all.

Where Pilot Protocol fits

The deadline in this guide is the same mechanism Pilot covered in a terminal link that expires at a set time, which also explains why a deadline is not a schedule. The loop on top of it is a polling pattern, and Claude Code's own docs point to pushed events as the alternative. Pilot Protocol, the networking stack for autonomous agents that shell comes from, takes the pushed approach between machines: its daemon can post events to a webhook for connections, trust changes, messages and files, so an agent on one machine reacts when something arrives instead of asking every 30 minutes. For a CI check on one pull request, a loop with a closing time is simpler, and that is the trade I would make for a single night.
