Anthropic published Claude Code 2.1.332 on GitHub early on 25 November 2026 (UTC). Among its 150 listed changes is one that names a setup more developers now run: Read, @-mentions and compaction used to hang on a named pipe that nothing writes to, "such as a .env mounted by a locked secrets manager". The release note says the read now fails after 20 seconds.

That setup is real and documented. 1Password can mount an Environment as a local .env file, and its developer docs say the contents are passed to the reading process on demand through a UNIX named pipe and never stored on disk. The feature works in 1Password for Mac and Linux. When a program reads the file you get an authorization prompt, and once you approve it, every process on the machine can read the file until 1Password locks or you turn the mount off. The Linux fifo(7) man page explains the hang: opening a FIFO normally blocks until the other end is opened too. While 1Password is locked, nothing opens the other end, so the reader waits.

If you share a coding agent's terminal with shell.online and also let a teammate open files from it, the same question comes up from the other side: does your .env travel with the files? This guide checks what kind of file your .env is, picks a file root that leaves it out, starts Claude Code with that root, and shows what the teammate can and cannot open.

How shell decides which files a viewer can open

File access in shell is off by default. You turn it on per session with one of two flags, both listed in shell help files and on the CLI reference:

shell --files claude
shell --files-root ./artifacts claude

--files opens the command's working directory. --files-root opens a directory you name instead, and passing it is enough on its own to turn file access on. The CLI opens that directory with Go's os.Root, which keeps every lookup inside it, and it rejects parent traversal and symlinks that point outside.

The rule that matters for a mounted .env is in cmd/shell/shared_files.go. When a viewer lists a folder, shell returns directories and regular files and skips everything else: symlinks, sockets, devices and named pipes. When a viewer asks to read a path, shell checks that it is a regular file within the size limit and answers with an error if it is not, without reading from it. The help text puts it in one line: "Only regular files beneath that root can be opened."

So a 1Password .env under the root never shows up in the Files panel. A plain .env under the root does, like any other file.

Step 1: Find out what kind of file each .env is

Run these in the project folder before you share anything. None of them opens the file, so none of them can hang on a pipe.

ls -l .env
test -p .env && echo "named pipe" || echo "not a named pipe"

In the ls -l output, the first character of the mode column is p for a named pipe and - for a regular file. The second line uses the -p primary of POSIX test, which is true only for a FIFO. Do not check a mounted file with test -f: a named pipe is not a regular file, so -f returns false for it.

Projects rarely have a single env file. List every regular file whose name starts with .env, since those are the ones shell would share:

find . -path ./node_modules -prune -o -type f -name '.env*' -print

find skips node_modules and prints paths such as ./.env.local or ./services/api/.env. A .env.example with placeholder values is fine to share. Anything else on the list holds real values, and it will appear in the Files panel if its folder sits under the root you choose.

The type check protects a mounted .env by accident of how 1Password builds it, not because shell knows what a secret is. A .env.local that a framework wrote, a .env you copied out of 1Password by hand, or a credentials.json next to them are regular files, and --files shares them with everyone who has the link. Pick the root so that no such file is under it.

Step 2: Give the session its own file root

The simplest root is a folder that holds only what you mean to show: test reports, a generated diff, a log. Create it and tell the agent to write there.

mkdir -p artifacts
find artifacts -type f -name '.env*'

The second command should print nothing. Create the folder before you start the session, because shell cannot open a root that does not exist. A relative path is resolved against the directory you run shell from.

If you would rather share the whole working tree with --files, the earlier post on sharing a terminal session without handing over the filesystem covers how the root and its limits were designed. For this guide I would keep the root narrow. It is easier to reason about a folder you filled yourself than about every file a project accumulates.

Step 3: Start Claude Code with that root

shell --name api-fix --files-root ./artifacts claude

shell starts Claude Code in the background and prints a card with the session's link. With file access on, the card has a Files row that reads artifacts · on demand: the root's folder name, and a reminder that nothing is sent until a browser asks for it. The browser is never given the full path, only that folder name.

If the teammate should watch but never type, start the session read-only and answer Claude Code yourself in the terminal you launched it from:

shell --read-only --foreground --name api-fix --files-root ./artifacts claude

--read-only makes the relay reject browser input for the whole session, and --foreground keeps the process mirrored in your own terminal so you can still answer its prompts. The help text is explicit that read-only links "may read files that were deliberately opted in", so read-only changes who can type, not what can be opened. The post on read-only links for a coding agent goes further into what view-only blocks.

Step 4: What your teammate sees in the Files panel

Once your teammate has the session open, a Files button appears in the terminal view. It opens a panel headed "Shared from this session", with the root's folder name as its title. Folders come first, then files with their sizes, at most 256 entries per folder. Previews are limited to 16 MiB and the Download button to 128 MiB.

A named pipe under the root does not appear in the list, and the browser has no entry to request. If something requests that path anyway, shell does not send its contents, because the read handler refuses any file that is not a regular file.

The files travel over the session's existing WebSocket, encrypted end to end like the terminal itself. shell's browser code encrypts session frames with AES-GCM through the Web Crypto API. According to shell help files, the relay routes request IDs and encrypted frame sizes, not paths or contents, and file sharing cannot be combined with --no-e2ee. The E2EE page describes what the relay can and cannot see in more detail.

Step 5: Keep the agent's own reads off the terminal

The Files panel is one way out for a secret. The terminal is the other. Whatever Claude Code prints, every viewer sees, and once you approve 1Password's prompt the mounted file is readable by any process until the vault locks. An agent that reads .env to debug a connection string can echo a value into the transcript.

Claude Code's settings guide shows a deny rule for exactly this case. Add it to ~/.claude/settings.json, or to the project's .claude/settings.json so teammates get it too:

{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)"
    ]
  }
}

Run /status in the session to confirm the file loaded. The permissions guide explains how deny rules combine across files. That guide says Read and Edit deny rules apply to Claude's built-in file tools, so watch for cat and env in Bash prompts as well.

What this setup does not do

  • It does not recognize secrets. shell filters by file type, not by name or content. A regular file holding a key is shared if it sits under the root.
  • It does not hide what the process prints. If a value reaches the terminal, everyone with the link has it. OWASP's secrets management cheat sheet says secrets should never be logged, and a shared terminal is a log that other people read live.
  • It does not stop the agent reading the pipe. 1Password's prompt is the gate there, and after you approve, every local process can read the file until the vault locks. 1Password also warns that mounted files are not built for concurrent readers, and the first process to read gets the secrets.
  • It does not give viewers different views. Every link holder sees the same root. To take access away, the post on revoking a shared link without killing the process covers shell password rotate.
  • It does not apply on Windows the same way, because 1Password's local mount is for Mac and Linux only.

The type check is a second line. The first is a root with nothing secret in it.

Where Pilot Protocol fits

shell's Files panel moves files from your machine to a person's browser. When the reader is another agent, Pilot Protocol covers that path. Its built-in data exchange service on port 1001 sends typed frames, including files with their names, which land in the recipient's ~/.pilot/received/ and wait there through disconnections. The same discipline applies: send the report, not the folder it was written in. If you want to see how Pilot encrypts those tunnels, its write-up on X25519 key exchange and AES-256-GCM in zero-dependency Go walks through the wire format. shell's source, including the file service quoted above, is on GitHub, and the security page lists what the product does and does not protect.
