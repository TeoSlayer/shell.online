OpenAI published Codex CLI 0.172.0 on 24 November 2026. Among its bug fixes is one line that matters to anyone who runs Codex unattended: codex exec resume now restores the saved sandbox permissions, the working directory and the workspace roots unless you override them. The same release also makes Codex report provider errors as soon as they arrive and name which API spend limit was reached, which is one of the usual reasons an exec run stops halfway.

The pull request behind the fix, openai/codex#62194, states the old behavior plainly. Resuming sent the current process's sandbox defaults as overrides, so a session started read-only could come back with workspace write access when the configured default was workspace. Nothing on screen warned you. A review you started with no write access could pick up again able to edit your files, which is the kind of quiet widening the OWASP entry on excessive agency lists as excessive permissions.

Codex prints the sandbox it is actually using at the top of every exec run. This guide runs the first exec run and its resume as read-only shell.online shares, so you can read that line from your phone for both runs, and covers the one window in which you have to read it.

What Codex Prints at the Start of an Exec Run

The non-interactive mode documentation says three things this guide relies on. codex exec runs in a read-only sandbox by default. While it runs, Codex streams progress to stderr and prints only the final agent message to stdout. And a resume keeps the saved working directory and sandbox permissions, with -C or --sandbox placed before resume to override them.

The progress on stderr opens with a summary block. In the 0.172.0 source it is a line reading OpenAI Codex v and the version, a row of dashes, then one line each for workdir, model, provider, approval and sandbox, the reasoning settings on Responses providers, and session id. The sandbox summary code fills the sandbox line with read-only, workspace-write followed by the writable roots in brackets (such as [workdir, /tmp, $TMPDIR]), danger-full-access, external-sandbox or custom permissions, with (network access enabled) added when the network is on. The same pull request makes Codex report the sandbox from the running thread, so on 0.172.0 the line describes the session as it was restored.

Both streams go to the terminal Codex runs in. Under shell.online that terminal is a pseudo-terminal, so the header, the progress and the final message all reach the browser. The stdin(3) man page explains why stderr and stdout are separate streams that can still share one terminal.

Step 1: Update Codex to 0.172.0

The fix is only in 0.172.0 and later. The Codex README gives both install routes:

npm install -g @openai/codex
brew install --cask codex
codex --version

Use whichever one you installed with. The last command should report 0.172.0 or later. If it reports an older version, the resume in Step 4 can still widen its sandbox, and the explicit override shown there is the only thing protecting you.

Step 2: Start the First Run as a Read-Only Share

From the root of the repository Codex should review, start the run under shell. The sandbox flag repeats the default on purpose, so the command line says what you meant:

cd ~/src/example-api
shell --read-only --name review-1 -- codex exec --sandbox read-only \
  "Review src/ for race conditions. List each one with file and line."

Everything after -- is the command shell runs, which follows POSIX utility syntax guideline 10: the first -- ends the options. shell starts Codex in the background in this directory, prints an unguessable browser link, a ten-character password and a QR code that carries both, and gives you your prompt back. --name review-1 labels the session in shell list, shell ls and the web app.

--read-only makes the link view-only: the relay rejects browser input. An exec run takes its instructions from the command line and needs no typing, so nobody holding the link has a reason to type into it. The share also closes by itself when Codex exits. The CLI reference lists every start option.

Step 3: Open the Link on Your Phone Before the Header Scrolls Away

Scan the QR code, or open the link on your phone and enter the password. The terminal page draws the run so far, and if you open it within the first moments of the run, the summary block is at the top. Read the sandbox: line. For this run it should say read-only. Note the session id: line as well, since it names this exact session for Step 4.

A viewer who opens the link late does not get the whole run. The shell CLI keeps the last 512 KiB of raw output for live delivery, but what it sends a newly joined browser is a rebuilt screen with 100 lines of scrollback above it. Feeding 300 numbered lines through that buffer at an 80 by 24 grid gives back lines 178 to 300. Once the run has printed more than a screen plus 100 lines, the summary block is gone for anyone who joins after that point. A page that stays connected keeps its own history (the link viewer sets an xterm.js scrollback of 10,000 lines, or 3,000 on a screen 760 pixels wide or less or one with a coarse pointer), but a reload starts over from the 100-line replay. Open the link right after you start the run and leave the tab open.

The two scrollback figures come from the viewer's code. The coarse pointer test is the CSS pointer media feature, which a phone's touchscreen matches, and scrollback is the xterm.js option that sets how many rows a terminal keeps above the screen. The mobile guide covers the rest of the phone view.

Step 4: Resume the Run as a Second Share

When the first run ends, its link goes offline. That happens when Codex finishes, and it also happens when Codex stops early on a spend limit, which 0.172.0 now names in the error. To continue, start the resume from the same directory as a new share:

cd ~/src/example-api
shell --read-only --name review-2 -- codex exec resume --last \
  "Rank the race conditions you found by how likely they are to fire."

--last picks the most recent recorded session. Codex filters that pick by working directory unless you add --all, so run the command from the directory you used in Step 2. If you ran other exec sessions in that directory since, use the session id you noted from the phone instead of --last: codex exec resume <SESSION_ID> "...".

Open the new link on your phone the same way and read the sandbox: line again. On 0.172.0 it should match the first run and say read-only, whatever your configured default is. If it says workspace-write, the resume did not restore what you started with, and you should stop it from the machine with shell kill and the session ID from shell list.

On an older Codex, or whenever you want the command line itself to say what the run may do, put the override before resume as the documentation says:

shell --read-only --name review-2 -- codex exec --sandbox read-only \
  resume --last "Rank the race conditions you found by how likely they are to fire."

The pull request describes the old code sending the current process's sandbox settings as overrides, so on an older version the override you type is the one the resume sends. The difference 0.172.0 makes is that leaving it out no longer hands the resume your configured default.

Step 5: Compare What You Asked For With What Codex Reports

The header is what Codex says it applied. The command line is what you asked for. While a run is live, shell list --json on the machine has the second one for every local session. This filter prints only the name, the access mode and the command, and leaves out the password field that the full JSON includes:

shell list --json | jq -r '.[] | [.name, .read_only, .command] | @tsv'

Each line is one session: review-2, true for a read-only link, and the full command with quoted arguments, prompt included. The jq manual documents the @tsv filter used here. If the command has --sandbox read-only and the phone shows workspace-write, believe the phone and stop the run. Because the prompt is part of the command, it appears wherever the command does, so keep secrets out of it.

The principle being checked is old. The NIST glossary entry for least privilege restricts a process acting for a user to the minimum access its assigned tasks need, and a resume that keeps a review read-only is that principle applied to one restart.

What This Setup Does Not Do

shell does not enforce Codex's sandbox and does not know about it. --read-only blocks browser input to the terminal. It does not stop Codex from writing files; only Codex's own sandbox does that.

The sandbox line is Codex reporting on itself. It is a useful check that a resume restored the setting you meant, not an independent audit of what the process can reach.

shell does not resume Codex sessions or keep a run alive past its exit. Each exec run is its own share with its own link and password, and a share closes when its task exits. A late viewer gets the screen plus 100 lines of scrollback, not the full output.

shell sends no alert when a run stops on a spend limit. You see it when you look.

Anyone with a link and its password can read everything Codex prints, including code it quotes from your repository. Payloads are end-to-end encrypted between the CLI and each browser, and the relay sees routing, size, timing and lifecycle metadata. If a link reached the wrong person, shell password rotate with the session ID changes the password without restarting the run, as the post on revoking a shared terminal link walks through. The security page and an earlier piece on read-only links for coding agents cover the rest of the model.

Where Pilot Protocol Fits

shell.online is developed by Pilot Protocol, which builds networking for autonomous agents. A sandbox line tells you what an agent may write; where it may connect is the other half of its limits. Pilot's write-up on getting a Pilot node online from a locked-down agent VM records what one tightly sandboxed agent could and could not reach, down to the proxy-only egress that finally worked. If you want Codex itself to talk to other agents, the guide to connecting Codex CLI to Pilot Protocol is the place to start.
