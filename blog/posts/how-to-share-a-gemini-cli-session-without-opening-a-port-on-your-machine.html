Gemini CLI 0.71.1 went out on 24 November 2026 with a single change: a cherry-pick of pull request 30420, which enforces bearer token authentication in the A2A server. The A2A server is the package that lets other programs drive Gemini CLI over HTTP using the Agent2Agent protocol, whose specification says servers must reject requests with invalid or missing credentials. According to the pull request, the server now reads a token from GEMINI_IPC_SECRET or CODER_AGENT_AUTH_TOKEN, compares it in constant time with Node's crypto.timingSafeEqual, and answers 401 to any request without it. If neither variable is set, every request gets 500. Requests must also carry a loopback Host header, and a loopback Origin when one is present, or they get 403. The code it replaced had placeholder checks: its bearer branch accepted the literal string valid-token.

The server already listened only on localhost. That is the point worth taking away from the fix. A port on 127.0.0.1 is reachable by every process on the machine, and a web page open in your browser can reach it too through DNS rebinding, unless the server checks Host and the Origin header the browser sends. The MCP transport specification spells out the same rule for local HTTP servers: validate Origin, bind to localhost, and authenticate every connection. A coding agent that can edit files and run commands is a bad thing to leave behind a port that only half checks who is calling.

This guide does three things. It shows you how to list what is listening on your machine, how to confirm that a Gemini CLI A2A server you run has the fix, and how to put Gemini CLI on your phone with shell.online without adding a TCP listener at all. The checks are for macOS and Linux, where I read the code paths.

Step 1: See what is listening on your machine

Before you share anything, find out which programs already accept connections. On macOS or Linux, lsof lists open sockets by process:

lsof -nP -iTCP -sTCP:LISTEN

-iTCP limits the list to TCP sockets, -sTCP:LISTEN keeps only the ones waiting for connections, and -nP prints addresses and port numbers instead of looking up names. Each row starts with the command name and its process ID and ends with the address, such as 127.0.0.1:41242 (LISTEN). An address of 127.0.0.1 or [::1] means loopback only. An address of * means every network interface, which includes your Wi-Fi.

On Linux you can use ss instead:

ss -ltnp

Here -l shows listening sockets, -t limits it to TCP, -n skips name lookups and -p names the process. Without sudo, both tools can only name processes that belong to you. Keep this list. You will compare against it in Step 4.

Step 2: Check the Gemini CLI A2A server, if you run it

If you only use the gemini command in a terminal and have never set up the A2A server, skip to Step 3. If you do run it, for an IDE integration or your own scripts, it is published as @google/gemini-cli-a2a-server, and the fixed version is 0.71.1. The v0.71.1 release lists the cherry-pick and nothing else.

The package's README now has an Authentication section. It says the token is read once at startup from the server's environment, never from a .env file, and that GEMINI_IPC_SECRET wins when both variables are set. From a checkout of the repository, the documented way to start it by hand is:

CODER_AGENT_AUTH_TOKEN="example-token-not-real" npm run start:a2a-server

That script sets CODER_AGENT_PORT=41242. Started any other way without that variable, the server asks the operating system for a free port, so read the port from the Step 1 list. Then test the three cases the pull request describes:

curl -i -H "Authorization: Bearer example-token-not-real" http://localhost:41242/listCommands
curl -i http://localhost:41242/listCommands
curl -i -H "Authorization: Bearer example-token-not-real" -H "Host: attacker.example" http://localhost:41242/listCommands

A fixed server answers 200 to the first, 401 to the second and 403 to the third. If the second request succeeds, the server is older than the fix. The README adds one more detail: requests that pass the Host and Origin checks but carry no token are limited to 100 a minute, after which the server answers 429.

Step 3: Start Gemini CLI under shell

If the reason you were looking at the A2A server was to reach Gemini CLI from somewhere other than your desk, you may not need a server at all. shell.online starts a program on your computer and gives you a browser link to its terminal. It does not wrap any agent protocol. It shares the screen and the keyboard.

Install it with the one-line installer, sign Gemini CLI in at the machine first, then start it through shell:

curl -fsSL https://shell.online/install | sh
shell --name gemini -- gemini

There is no shell gemini shortcut the way there is shell claude or shell codex, so you pass the command after --. --name labels the session in shell list and the web app. shell prints a link, a password and a QR code that carries both, and runs Gemini CLI in the background. Closing the browser does not stop it. The session ends when gemini exits.

Step 4: Confirm the share added no TCP listener

Run the Step 1 command again:

lsof -nP -iTCP -sTCP:LISTEN

Compare it with the list you kept. On macOS and Linux, starting a session should not add a row for shell. To see what shell does have open, ask for its TCP sockets by process ID:

lsof -nP -a -p "$(pgrep -d, -x shell)" -iTCP

pgrep -d, -x shell prints the IDs of every process named exactly shell, separated by commas, and -a tells lsof that both conditions must hold. What you should see are connections in the ESTABLISHED state to a remote address on port 443. Those are outbound: the CLI dials the relay over HTTPS and a secure WebSocket, which is why the platform notes list a working PTY and outbound HTTPS and WebSockets as what a supported machine needs. Nothing on the internet connects in to your computer.

The parts of shell that do talk to each other on your machine, the background daemon and each session, use Unix domain sockets. You can list them:

ls -la "/tmp/shell-online-$(id -u)"

You should see daemon.sock and one <ID>.sock per running session, each with mode srw-------. In cmd/shell/local_transport_unix.go and daemon_unix.go, shell sets each socket to 0600, refuses to use the directory if it is not owned by your user, and resets the directory to 0700 if it finds looser permissions. The unix(7) man page notes that on Linux, connecting to a stream socket requires write permission on the socket file. A web page has no way to open a Unix socket at all, so the DNS rebinding route that the Gemini fix closes does not apply here. If you set SHELL_ONLINE_RUNTIME_DIR, the sockets live in that directory instead.

The one TCP listener shell does open is during sign-in. shell auth binds 127.0.0.1 on a port the operating system picks, so the browser can hand the approval back. It closes when sign-in finishes or the wait runs out: five minutes in v0.25.0, raised to fifteen in the changelog's Unreleased section. The callback checks a random state value, and the flow uses a PKCE code verifier that never leaves the CLI. If you run Step 1 while signing in, that row is expected. On Windows the daemon uses a named pipe instead, and starting a background session briefly opens a loopback listener that requires a token; this guide's checks cover macOS and Linux only.

Step 5: Open it on your phone and know what the relay carries

Scan the QR code, or open the link and type the password. On a phone, the mobile view shows a key bar with esc, tab, the four arrows, enter and ctrl-c under the terminal, which is enough for any menu that moves with the arrow keys and confirms with enter. Typing works as on any terminal.

Terminal traffic is end-to-end encrypted by default. The security model says the host encrypts terminal payloads before the relay forwards them, and the relay carries authenticated ciphertext plus connection metadata such as IP addresses, timing, message sizes and the terminal's grid size. The encryption page has the details, and an earlier post covers what the relay sees and what it can no longer read. Read both before you share a link with anyone else.

Step 6: End the share when you are done

From the machine, list the running sessions and stop the one you started:

shell list
shell kill -- <ID>

shell list prints each session's ID with its name and uptime. shell kill stops the process and closes its link. If you want Gemini CLI to keep running but a link you handed out to stop working, shell password rotate <ID> revokes the password and prints a new one. The post on revoking a shared link without killing the process walks through that case. Every command is in the CLI reference.

What this setup does not do

  • It does not secure servers that Gemini CLI or its MCP servers open. shell starts gemini and shares its terminal. Whatever ports the agent opens are its own, and Step 1 is how you find them.
  • It does not replace the A2A server. Another program cannot send Gemini CLI a task through a shell link. A person with the link and password can read the screen and type.
  • It does not protect the sockets from you. Any process running as your user can connect to them, which is how shell attach works on the same machine. The permissions keep out other users, not other programs of yours.
  • An interactive link lets its holder type with Gemini CLI's permissions. If someone only needs to watch, start the session with shell --read-only, as in this earlier guide to a read-only link for a coding agent.
  • The computer has to stay awake and online. A sleeping host cannot be reached by anything.

Where Pilot Protocol fits

The A2A server exists because some jobs really are one agent calling another, and a terminal link is the wrong tool for those. shell.online is built by the team behind Pilot Protocol, a networking stack for agents, and its blog has a walkthrough of serving A2A agent cards over Pilot tunnels. There the agent's card names a Pilot address instead of a public URL, peers resolve a private agent only once they are trusted, and the tunnel is encrypted after a signed handshake. If you want Gemini CLI itself on that network, the guide to connecting Gemini CLI to Pilot Protocol adds Pilot as an MCP server with one command. The Gemini CLI documentation covers the rest of its MCP setup.
