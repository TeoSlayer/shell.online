OpenAI released two models on 17 November. GPT-6.2 Astra is the one it pitches for the hardest work, and GPT-6.2 Sol is the cheaper model meant for everyday tasks. The number that matters to anyone paying for agent runs is a coding one: as Digital Trends reported from OpenAI's announcement, OpenAI says Sol finishes within half a percentage point of Astra on FrontierCode 2.0 at roughly a fifth of the cost. Let's Data Science lists Astra's API price as $8 per million input tokens and $40 per million output tokens, and points out that the benchmark figures are OpenAI's own claims. Digital Trends gives Sol's price as $2 and $10, unchanged from the model before it.

Codex picked both models up within days. The Codex 0.171.0 release, published on GitHub on 20 November (UTC), adds GPT-6.2 Sol and Astra to its model catalogs, and the pull request behind that change makes gpt-6.2-sol the default catalog selection. If you upgrade and have never pinned a model, your next Codex session may already be running on Sol.

A vendor benchmark is a fair place to start and a poor place to stop. The test that counts is your repository and your prompt. This guide runs one read-only Codex review on both models at the same time, each in its own named shell.online session, so you can follow both from a phone, answer either one if it stops to ask you something, and compare what each found before you decide which model stays your default.

Step 1: Upgrade Codex and check both tools

Install the new Codex release and confirm the versions on the machine that will run the reviews:

npm install -g @openai/codex
codex --version
shell --version

The install line is the one in the Codex README, which also lists brew install --cask codex for Homebrew. codex --version should report 0.171.0 or later. Older builds do not list the two GPT-6.2 models in their catalog.

shell --version prints shell followed by the version; the current release is 0.25.0. If the command is missing, the install line in the shell.online README for macOS and Linux is curl -fsSL https://shell.online/install | sh, and the CLI page lists every command. The source for everything below is in the shell.online repository on GitHub.

Step 2: Write the prompt once

Both runs should get exactly the same instructions, so put them in a shell variable from the root of the checkout you want reviewed:

cd ~/src/demo-shop
git switch feature/retry-checkout
PROMPT='Review the changes in git diff main...HEAD. List real bugs with file and line. Skip style comments. Do not edit files.'

The single quotes keep every character literal, as the POSIX shell rules for quoting require, so nothing in the prompt is expanded early. The three dots in main...HEAD matter: the git diff manual says that form compares the branch against its merge base with main, which is the change set a reviewer wants.

Keep secrets out of the prompt. As Step 5 shows, shell records the whole command line, prompt included.

Step 3: Start the Sol review

shell --name sol-review -- codex --model gpt-6.2-sol --sandbox read-only "$PROMPT"

Everything before -- belongs to shell and everything after it is the command shell starts. shell parses its options with Go's flag package, and the flag package documentation says parsing stops at the first non-flag argument or after the terminator --. That is why --model and --sandbox reach Codex instead of being read by shell.

The two Codex options come from the Codex command reference. --model overrides the model set in your configuration. --sandbox sets the policy for shell commands the model generates, and takes read-only, workspace-write or danger-full-access. With read-only, both reviews can read the same checkout without either one editing a file under the other. The prompt goes in double quotes so it arrives as one argument.

shell starts Codex as a new background process and prints a card. The parts you need look like this, with your own link, password and ID in place of the brackets:

  Name       sol-review
  Open       <link>
  Password   <ten characters>
  Vault      saved to your account vault
  Access     view and type · end-to-end encrypted
  Session    <ID> · background
  Closes     when the task exits

  Rejoin     shell attach <ID>
  Stop       shell kill -- <ID>

The Vault line says not linked · run shell auth on a machine you have not linked to an account. The link and the password together open the session, and as the Access line says, the link is interactive: whoever holds both can type into Codex. The encryption page explains how the password protects what the relay carries.

Step 4: Start the Astra review the same way

shell --name astra-review -- codex --model gpt-6.2-astra --sandbox read-only "$PROMPT"

Only the name and the model change. The model names gpt-6.2-sol and gpt-6.2-astra are the ones the Codex pull request adds to the bundled catalog. You now have two Codex processes on this machine, each reading the same branch, each behind its own link and its own password.

shell has no model setting. It passes the arguments after -- to Codex unchanged, so a run started without --model uses whatever your Codex configuration says, and on 0.171.0 with nothing configured that is Sol. If you compare a bare shell codex against an Astra run, you may be comparing Sol with Astra without meaning to. Name the model on both command lines.

Step 5: Check what each session is running

shell list
shell list --json | jq -r '.[] | [.name, .command] | @tsv'

shell list prints one row per active share on this machine with the columns ID, NAME, UPTIME, RELAY, CLOSES, ACCESS, COMMAND, SHARE URL and PASSWORD. In a terminal narrower than 132 columns it switches to a compact layout with one block per session. Both layouts shorten the command, so the model flag can be cut off. The wide table ends with the line Long URLs and full credentials: shell list --json.

The JSON form carries the whole command line. The jq manual describes -r as printing strings without JSON quoting and @tsv as turning each array into one tab-separated line, so the second command prints two lines like these:

sol-review	codex --model gpt-6.2-sol --sandbox read-only "Review the changes in git diff main...HEAD. List real bugs with file and line. Skip style comments. Do not edit files."
astra-review	codex --model gpt-6.2-astra --sandbox read-only "Review the changes in git diff main...HEAD. List real bugs with file and line. Skip style comments. Do not edit files."

That is your record of which run got which model and which prompt. shell puts double quotes around any argument that contains a space when it records the command. The JSON also holds each session's password in the e2ee_password field, so do not paste the raw output into a chat or a ticket.

Step 6: Open both runs on your phone

The quickest route is the web app. Run shell auth once on the machine, approve the request in the browser, and every share you start from then on appears in your account. Sessions started before you linked do not show up, so if you link now, start the two reviews again. On the phone, sign in at app.shell.online and open both sessions. The web app keeps up to eight open sessions as tabs, labelled with the name you gave each one, so sol-review and astra-review sit next to each other. The tab badges described in the post on the passive pulse tell you which of the two has new output.

Without an account, open each Open link from Step 3 on the phone and type its password. Either way, the mobile guide is clear that a signed-in session listing is not a substitute for a terminal's password. The web app can recover a password from your account vault when the password was saved there, which is what the card's Vault line reports. If it said the password was not saved, keep the card at hand.

When a review finishes its turn, type /status into that session. In the Codex source for 0.171.0, /status is described as showing the current session configuration and token usage. Use it to check each run's configuration and to read its token counts. If you sign in to Codex with an API key, those counts and the per-million prices above give you the cost of each review.

Step 7: Compare the findings, then close both links

Read the two answers against the diff, not against each other. For each bug a model reports, open the file and line it names with git diff main...HEAD -- <path> and decide whether it is real. Digital Trends also reported that testing found the new models sometimes failed to tell users about problems they ran into while completing tasks, which is one more reason to check each claim rather than count them.

When you have what you need, copy the findings out, then leave each Codex session with /quit, or stop it from the machine:

shell kill -- <ID>

Use the ID from the card or from shell list. The card said Closes when the task exits, and the mobile guide puts it the same way: the session ends when its process exits. Once Codex quits, that link stops showing the review. If you would rather have each answer in a file, run the reviews with codex exec, which the command reference says writes the final message to a path you give with --output-last-message.

If you shared either link with a teammate and want them out before you are done, rotating the session password with shell password rotate <ID> revokes the old password without stopping the review.

What this setup does not do

  • shell does not score, rank or diff the two answers. It shows you two terminals and records the two command lines. The judgment is yours.
  • It does not count tokens or work out cost. The numbers come from Codex's /status, and the prices are OpenAI's as reported by the press.
  • It does not isolate the runs from each other. Both use the same machine, the same checkout and the same Codex sign-in. The read-only sandbox covers commands the model generates. It does not stop a person who has a link and its password from typing into the session; start the share with --read-only before you give a link to someone who should only watch.
  • It does not make one run a fair benchmark. One prompt on one branch is a sample of one, and a second attempt on the same model can find different things.
  • It does not hold the review open after Codex exits. The session ends with the process, so copy what you want before you quit.

The security page sets out who can see and type into a session, and the post on naming sessions covers --name and shell ls when the two runs live on different machines.

Where Pilot Protocol fits

shell.online is developed by Pilot Protocol, a networking stack for autonomous agents. shell handles one half of this job: getting two terminals in front of a person. The other half, where one agent hands its findings to another without you copying text out of a phone, is the part Pilot is for. The Pilot messaging guide describes the ways agents on the network exchange data, from stream connections to stored messages, files and pub/sub, and the guide to connecting Codex CLI to Pilot over MCP shows how to add Pilot's hosted MCP server to Codex with one command, after which Codex can message other agents. A Sol review that sends its list to the agent that will fix the bugs is a small step from there.
