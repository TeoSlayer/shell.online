On 12 November OpenAI published Codex Security 0.10.0, the CLI and TypeScript SDK that scans a codebase for vulnerabilities, validates what it finds and drafts patches. The repository is Apache 2.0 licensed. Two changes in this release matter if you run scans that take a while. An interrupted Standard scan can now continue from a saved checkpoint with codex-security scans resume SCAN_ID, keeping its usage and its budget, which came in with pull request 2610. And bulk or component scans accept --max-total-cost, one estimated budget shared across repositories or components.

The budget is the part that needs a person. The CLI guide says that when a single interactive scan reaches 80% of its --max-cost limit, the full-screen dashboard offers a higher total. Work continues while you decide, and the old limit stays in force until you save a new one. CI, JSON, headless and verbose runs never ask. So the prompt only appears in a real terminal, and only someone looking at that terminal can answer it before the scan reaches the old limit and stops.

This guide runs a Codex Security scan inside shell.online, so the dashboard is on your phone as well as your desk. You will start the scan with a persistent link, answer the budget prompt from the phone's key bar, avoid the one tap that cancels the scan for good, and bring an interrupted scan back on the same link.

Step 1: Install shell and Codex Security

On the computer that holds the checkout, install shell with the installer from the shell.online repository, then the scanner from npm with a global install:

curl -fsSL https://shell.online/install | sh
shell --version
npm install --global @openai/codex-security
codex-security --version
codex-security login

The installer checks release checksums, and shell --version prints what you got. The npm package provides codex-security and a short alias, cs. codex-security login signs you in with ChatGPT.

Step 2: Choose an output folder and a state file

Codex Security wants an empty output directory outside the scanned directory and outside its Git worktree. shell wants a state file for --persistent, which holds the session's host credentials, its browser password and its decryption material. Neither belongs in the repository:

mkdir -p ~/scans ~/.shell-states
chmod 700 ~/.shell-states

Do not create the output folder itself: the scanner creates it, private to you, and refuses one that already has files in it. Keep the state file name for later: re-running a command with the same --persistent file brings back the same link and the same password, which is what makes Step 5 work.

Step 3: Start the scan inside shell

From the checkout, wrap the scan in shell. The example repository, cost and paths are invented:

cd ~/src/payments-api
shell --persistent ~/.shell-states/payments-scan.json --name "cs payments" -- \
  codex-security scan . --max-cost 25 --output-dir ~/scans/payments-0.10

Everything after -- is the scanner's command line. shell starts it in a pseudo-terminal on this machine, prints a browser link, a ten-character password and a QR code, and hands your prompt back while the scan runs in the background. --name labels the session in shell list and in the web app. --max-cost 25 tells Codex Security to stop the scan and its workers once the estimated cost passes 25 US dollars. For OpenAI models the estimate uses the published OpenAI API rates. The guide is plain that requests already in flight can finish above it.

Running inside shell matters for the prompt. In the 0.10.0 source the scanner offers a budget increase only when its standard input is a terminal. shell gives the scan a real pseudo-terminal, so the dashboard behaves as it would in your own window. If you redirect output or add --headless, you get plain status lines and no prompt, with or without shell.

The link and password together are an access credential. Anyone holding both can type into this scan, including the keystroke that ends it. Send them over separate channels if you send them at all, and see the security page and the encryption details for what the relay can and cannot read.

Step 4: Read the dashboard and answer the prompt on your phone

Scan the QR code, or open the link on the phone and type the password. The scan's dashboard draws in the browser through xterm.js as it does on the host, and the phone guide covers the rest of the mobile view.

Under the terminal, on a screen 760 pixels wide or narrower, or any touch screen, shell shows a key bar: esc, tab, four arrows, enter and ctrl-c. Each sends the byte a keyboard would. The bar is disabled on read-only links, while the page waits for the session key, and while the session is not connected, so a greyed-out bar tells you something before you tap it.

Tap the terminal to raise the phone's keyboard and press d to switch the dashboard to its details view. There, a shows all sources, m the main scan, and 1 to 9 a single worker. The CLI guide suggests the details view for scrolling through the full readings on a short terminal, which a phone held upright is.

When the estimate passes 80% of the limit, the dashboard asks for a higher total. You have three answers:

  • Type a plain number, such as 40, and tap enter. It has to be above the current limit and above the cost estimated so far. Anything else, including a dollar sign, gets the reply "Enter a finite total above" followed by the minimum, and the prompt stays open.
  • Tap enter with nothing typed to keep the limit.
  • Tap esc to dismiss the prompt and keep the limit.

The scan keeps working the whole time. If you ignore the prompt, the old limit applies and the scan stops once the estimate crosses it.

The ctrl-c key cancels the scan, and a cancelled scan cannot be resumed. It sits on the same strip as enter. In the 0.10.0 source, Ctrl-C or Ctrl-D typed into the budget prompt closes the prompt and interrupts the scan, and the CLI treats the first SIGINT or SIGTERM it receives as a cancellation (cli-signals.ts). It prints codex-security: Scan canceled by Ctrl-C. and exits with status 130, or 143 for SIGTERM. The guide is explicit that completed, failed and cancelled scans need scans rerun, which starts a new scan with fresh discovery and does not continue the old one. shell kill is no gentler: it sends SIGTERM to the scan's process group and, on Unix, SIGKILL two seconds later if the scan is still running.

Step 5: Bring an interrupted scan back on the same link

The resumable case is a scan that stopped without recording a cancellation. The guide names one: the connection fails after the session is saved, and the CLI prints the resume command itself. Because the CLI records a cancellation itself when it gets a signal, a process that dies before it can, from a SIGKILL or a power cut, should also leave the scan marked running. Either way, when the scanner exits, the shell session closes with it, and the link on your phone goes offline.

Back at the machine, find the scan:

cd ~/src/payments-api
codex-security scans list --scan-root ~/scans

The list prints each full scan ID. For a running Standard or Deep scan with a saved recipe and its original session, it also prints the resume command, and it labels a running scan whose last activity is more than 24 hours old. Resume it under the same state file:

shell --persistent ~/.shell-states/payments-scan.json -- \
  codex-security scans resume SCAN_ID

shell reuses the session identity, password and URL from the state file, so reload the tab already open on your phone and type the same password. The --name from the first run carries over too. The scanner keeps the scan ID, completed workers, artifacts and accumulated cost, and continues in its original Codex session with the same --max-cost limit and --max-time deadline. Work since the last checkpoint may be done twice.

Three things stop this command. The scanner refuses unless the checkout identity, revision and contents still match, so do not switch branches or edit files while a scan is waiting. shell refuses if you change the access mode: a state file created without --read-only answers a later run with --read-only by saying the access and encryption mode do not match. And if the machine crashed and left a local session record or control socket behind, shell blocks the resume until you look at it and recover it yourself. Nothing restarts it for you.

When the scan completes, its results folder holds report.md, findings.json and a SARIF export under exports/results.sarif when that optional write succeeds.

Step 6: Decide who else holds the link

The budget prompt needs an interactive link, because a --read-only session blocks browser input for every viewer, the owner included. That makes this setup a poor fit for a teammate who only needs to watch. If you hand them the link and password, they get the same ctrl-c key you have.

If a watcher matters more than answering from the phone, start a separate scan with --read-only and its own state file. Then answer its prompts at the computer with shell attach, using the ID from shell list, and detach with Ctrl-X, then D. A read-only link for a training run walks through that pattern. If you shared the interactive link and want it back, shell password rotate <ID> changes the password and disconnects current viewers without stopping the scan, as the post on revoking a link explains.

What this setup does not do

  • shell does not read the cost or tell you that the prompt is waiting. There is no push notification. You see the prompt when you look.
  • It does not pause a scan. A persistent link is a stable identity, not a process checkpoint, as the reliability page says. The resume comes from Codex Security's own checkpoint.
  • It does not make Ctrl-C safe. From the phone, the keyboard or shell kill, a signal cancels the scan. The signal(7) man page explains that SIGKILL cannot be caught or ignored, and the POSIX terminal interface covers how a terminal turns Ctrl-C into SIGINT.
  • It does not keep a sleeping or offline computer reachable. The host has to stay awake and online for the scan to run and for the link to work.
  • It does not change what Codex Security sends to its model provider. End-to-end encryption covers the terminal traffic between your machine and the browser, nothing else.
  • It does not cover batch budgets. The docs describe the increase prompt for a single interactive scan, so do not expect it from a --max-total-cost bulk run.
  • It does not judge the findings. The guide states that a completed scan does not mean every file was examined. A scanner is one input to a process like NIST's Secure Software Development Framework, and OWASP's page on source code analysis tools lists the limits such tools share.

Where Pilot Protocol fits

shell.online is developed by Pilot Protocol, an open source network stack for autonomous agents. A scanner that runs for a long time and spends money as it goes is still an agent, and Pilot's piece on network security for multi-agent systems argues for layers of visibility and guardrails rather than one control. Here the cost limit is a guardrail and the link is visibility. In my view the cap is only worth setting if someone can see the prompt in time to answer it.
