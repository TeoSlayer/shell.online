On 12 November 2026 Anthropic opened a private beta of self-hosted Claude Managed Agents. Until now a team could keep only the sandboxes on its own machines, through self-hosted sandboxes. Now the whole service moves too. According to the self-hosted Managed Agents documentation, you run the API server and agent loop (cma-server), a PostgreSQL 16 or later database for agents, sessions and session history, and the workers that run the agent's shell and file tools. A console on your server signs people in through your own identity provider. Model calls still go out, to Anthropic by default or to a provider you pick.

Anthropic's announcement gives the reason plainly: some teams need every part of the agent service inside their own environment, not only the sandbox. If your team is one of them, look at what else your agents touch. A terminal link that a teammate opens to watch a Claude Code run is one of those things. If the agent runs inside your perimeter but the list of sessions, the machines that can start them and the sign-in all live on someone else's service, the perimeter has a gap in it.

shell.online can be run in two self-hosted pieces. The relay that carries terminal traffic is covered in two earlier posts, one on running it on one Docker box and one on choosing it over the Cloudflare Worker. This guide covers the other piece: the accounts app behind app.shell.online. You will register an OpenID Connect client with your provider, start the app and its PostgreSQL database, point the CLI at all three of your addresses, and check that nothing still goes to the hosted service.

What the accounts app holds, and what it never sees

The accounts app README describes it as optional: it provides accounts, organizations, linked machines, session lists, comments and browser-started sessions, and the CLI and relay work without it. When a linked machine starts a session, shell help auth lists what is published to the account: the share URL, the command name, the host name and the timing. It never publishes the terminal contents or the encryption key, because the key lives in the URL fragment and the fragment is stripped before the URL is sent.

The app also carries browser terminal traffic, but only as a pass-through. The relay accepts a websocket only from its own origin, and a browser sets the Origin header from wherever the page came from. So the app's server forwards /relay/* to your relay and rewrites the Origin on the way. The comment on that proxy in app/server/lib/relay-proxy.ts states that frames are encrypted in the browser first, so the proxy sees the same ciphertext the relay sees. The end-to-end encryption page explains that model.

By default, app.shell.online holds the session list, the machine list and the sign-in. After this guide, your own database holds them.

Step 1: Run your own relay first

The app needs a relay to forward to, and there is little point in a private session list for sessions that cross the hosted relay. The self-hosting page has the full steps. The short version, on a host whose DNS already points at it:

git clone https://github.com/TeoSlayer/shell.online.git
cd shell.online/standalone
SHELL_ONLINE_PUBLIC_URL=https://relay.example.com \
SHELL_ONLINE_SITE=relay.example.com \
docker compose up -d --build

Caddy in that stack gets a certificate through its automatic HTTPS once DNS and ports 80 and 443 are ready. curl https://relay.example.com/api/health should answer before you go on.

Step 2: Register a public client with your identity provider

The app can sign people in with Firebase, which is what the hosted service uses, or with any OpenID Connect provider. With OIDC it uses the authorization code flow with PKCE (RFC 7636), and registration, passwords and account recovery stay with your provider. In your provider's admin console, create one client with these settings, taken from the app README:

  • A public client, with no client secret, because the code runs in a browser.
  • PKCE with the S256 method.
  • Redirect URI https://shell.example.com/auth/callback, where https://shell.example.com is the public address the app will have (WEB_ORIGIN below).
  • Allowed web origin https://shell.example.com. This one is easy to skip. The app renews a sign-in before it expires from a hidden iframe, and that renewal needs the origin allowed.

Note the issuer URL and the client id your provider gives you. The server checks every ID token against that issuer and expects the client id as the audience. It finds the signing keys through the provider's OpenID Connect discovery document unless you set OIDC_JWKS_URI yourself. The token rules themselves are in OpenID Connect Core.

Step 3: Fill in the app's settings and start it

The app ships with a Compose file that runs it next to PostgreSQL 16. From the repository:

cd shell.online/app
cp .env.example .env

Then edit .env. Leave the Firebase lines blank and set these:

VITE_OIDC_ISSUER=https://idp.example.com/realms/eng
VITE_OIDC_CLIENT_ID=shell-online-app
RELAY_URL=https://relay.example.com
WEB_ORIGIN=https://shell.example.com
POSTGRES_PASSWORD=change-this-before-you-start
TRUST_PROXY=0

The two VITE_ values are compiled into the browser bundle. Vite's guide on environment variables explains why: they are bundled into the source at build time. The Compose file passes them as build arguments, and it passes RELAY_URL to both the client build and the server. It also hands the issuer and client id to the server as OIDC_ISSUER and OIDC_AUDIENCE. Because of the build step, any change to these values needs a rebuild, and a restart is not enough:

docker compose up --build -d
curl http://localhost:8080/api/health
curl http://localhost:8080/relay/api/health

docker compose up waits for the database's health check before it starts the app. The first curl asks the app itself and does not touch the database. The second goes through the app's relay proxy to your relay, so it shows the app can reach it. The app's own boot test expects a 502 from that path when nothing is listening at the relay address.

The container listens on plain HTTP on port 8080. Put your usual TLS proxy in front of it at https://shell.example.com. Set TRUST_PROXY=1 only if that proxy replaces the X-Forwarded-For header. The Compose file notes that trusting it otherwise lets any caller pick a new address per request.

Step 4: Point the CLI at all three addresses

The CLI knows three services: the relay, the accounts API and the web page that approves a login. The app's client and server ship in one image on one origin, so the last two are the same URL. On each machine that runs agents:

export SHELL_ONLINE_SERVER=https://relay.example.com
export SHELL_ONLINE_ACCOUNTS=https://shell.example.com
export SHELL_ONLINE_WEB=https://shell.example.com
shell auth

When either account address is not the production one, shell auth says so before the browser opens:

  Approving at https://shell.example.com
  Tokens from  https://shell.example.com

If that block does not appear, a variable did not reach the command, and you are about to link the machine to app.shell.online. Press Ctrl-C and fix the environment first. If it does appear, the browser opens your app, your provider signs you in, and the machine is linked. The credential file records the accounts server it was issued by, and later commands such as shell ls read it from there. To check that field without printing the tokens next to it (on Linux the file is under ~/.config):

jq -r .server "$HOME/Library/Application Support/shell-online/credentials.json"

That path is the macOS one. The CLI puts the file in Go's user config directory, or wherever SHELL_ONLINE_CONFIG says.

The relay address is not remembered. shell help auth warns that every address defaults to production, so setting only some of them aims the rest at the real service. The credential file keeps your accounts server, but nothing keeps your relay. A later shell claude run from a terminal without SHELL_ONLINE_SERVER starts its session on https://shell.online, and your own app still lists it. Put the three exports in your shell profile, not in one terminal. Also check that RELAY_URL in the app's .env no longer holds the example value, which is the hosted relay.

Step 5: Carry the addresses into the background service

shell auth asks once whether your signed-in browser may start sessions on this machine. The first yes also installs a background service, so the machine stays reachable after a restart. A service starts from the operating system and not from your shell, so it would not see your exports. The CLI copies six variables into the service definition when it installs it: SHELL_ONLINE_LOCAL, SHELL_ONLINE_ACCOUNTS, SHELL_ONLINE_SERVER, SHELL_ONLINE_WEB, SHELL_ONLINE_CONFIG and SHELL_ONLINE_RUNTIME_DIR. On macOS they go into the LaunchAgent's EnvironmentVariables, and on Linux into Environment= lines of the systemd user unit.

If you link while the exports are set, that is done. If a service was installed earlier for the hosted service, it still carries the old environment. Reinstall it from a terminal where the exports are set:

shell service uninstall
shell service install
shell daemon status

Sessions you start from the browser are launched by this daemon and inherit its environment, so this step decides which relay they use. Then start something and look at where it went:

shell --name relay-check bash
shell list
shell ls

shell list shows the local share URL, which should start with https://relay.example.com. shell ls asks your app for the account's sessions on every machine, and relay-check should be among them. Open the link on a phone and enter the password; the page now comes from your relay, and the mobile guide applies as before. shell kill -- <ID>, with the id shell list printed, stops it. The CLI reference has every flag used here.

What this setup does not do

  • It does not keep your agent's model traffic inside. shell.online carries the terminal. Claude Code, Codex or anything else you wrap still sends prompts to its own provider. Anthropic's documentation makes the same point about its server: the conversation, including tool inputs and results, goes to your inference provider on every model call.
  • It is not a cluster. The operator guide describes the standalone relay as a single node, and warns against running more than one replica against one state volume. It does not include the hosted analytics dashboard.
  • It does not give you the native MCP channel. The self-hosting page names accounts and native MCP as separate deployments, and native MCP comes with the Cloudflare Worker relay.
  • It does not handle account recovery. With OIDC, registration, passwords and recovery belong to your provider. Invitation email works only if you configure a mail provider (MAIL_API_KEY and MAIL_FROM).
  • It does not back itself up. The postgres volume holds your accounts, machines and session list. A pg_dump on a schedule is the minimum. The relay's relay-state volume needs its own backup.
  • It does not change who can type into a session. Read-only links, passwords and rotation behave as on the hosted service. The security page and the post on sealed team sharing cover those.

Where Pilot Protocol fits

shell.online is developed by Pilot Protocol, a networking stack for autonomous agents, and its own directory can be run the same way. The Pilot docs on self-hosting the registry tell you to run your own rendezvous and point your daemons at it, and the registry can check OIDC tokens itself. The post on building a private agent network for your company goes further: a self-hosted rendezvous, private networks, and the outbound feeds, telemetry and updater turned off. If your agents talk to each other as well as to people, that is where to look next. shell.online then covers the human side: a link to the terminal that someone can open on a phone, through servers you run.
